# EG Voice 0.2.4: Design Lab и корректные ошибки голоса

26 сентября 2026. Тестовая версия, не подтверждённое исправление связи у пользователя.

## Что изменилось

- Авторизация: двухколоночный экран, шрифты Cabinet Grotesk / General Sans, логотип и анимация из Design Lab, мобильная компоновка.
- Вход: показ пароля, Caps Lock, блокировка повторной отправки, запрет отправки офлайн; при 401 email сохраняется, пароль очищается и получает фокус.
- Регистрация: порядок ник → email → пароль, ник 2–24 символа, подсказка длины пароля, индикатор состава пароля без обещаний безопасности, перенос email на вход после ошибки.
- Голос: плитки 16:11, аватар 88 px, зелёная обводка только при реальной активности участника, без декоративной волны; плитка приглашения, профиль по нажатию, локальная громкость собеседника.
- Подключение: шаги сервера, микрофона и публикации основаны на реальных стадиях клиента. Нет выдуманных задержек, географии или статуса «сервер исправен».
- Восстановление: ограничено 20 секундами, затем конечная ошибка, освобождение микрофона и явный повтор. Ошибка публикации больше не маскируется сообщением «восстанавливаем».
- Диагностика: история ICE/connection/signaling до закрытия соединения, события signal/reconnect/disconnect, начальные шаги получения токена и соединения. Без SDP, IP, TURN-ключей и токенов.
- Приглашения: открываются из шапки голоса и пустой плитки; показывают фактический срок, полученный от API. При принятии микрофон не включается автоматически.
- Участники: HTTP-обновление раз в 10 секунд при недоступном realtime, состояния загрузки/ошибки; участник активного звонка не обозначается офлайн по устаревшему lastSeen.

## Что известно о сбое

Скриншот 0.2.3: route=auto, connection=compatible, capture/worklet/resume завершились за 25 мс. На этапе publish через ~30 сек получен ConnectionError: publication of local track timed out, no response from server. Четыре RTC-соединения уже закрыты; такой снимок не определяет первопричину.

Подключённый аккаунт LiveKit и прежнее приложение используют один адрес: wss://egvoice-7mii3mms.livekit.cloud. Через свежий короткоживущий токен коннектора независимый браузерный SDK-тест в облачной среде подключился и опубликовал микрофон. Это исключает универсальную недоступность проекта в момент теста, но не подтверждает доступность из сетей пользователя и друга. Корневая причина их сбоя остаётся открытой.

## Проверки

- TypeScript и production build.
- 10 unit-проверок голосовой политики, приватности диагностики и RTC-истории.
- 4 unit-проверки приглашений.
- 23 UI-проверки: реальный AudioWorklet/capture, тестовый RTC-транспорт; включая конечную ошибку после 20 сек и повтор.
- Отдельная проверка авторизации: 401, показ/скрытие, офлайн, невалидная регистрация, мобильные 375 px, тёмная/светлая темы, reduced motion.
- Независимый реальный LiveKit SDK-тест: успешное подключение и публикация в изолированную диагностическую комнату; соединение завершено, захват остановлен.

Windows-результат сборки прилагается отдельно после CI. Локальные UI-тесты не заменяют разговор двух людей из целевых сетей.

## Ещё не готово

- Серверный поиск друзей и заявки реализованы в исходниках, но старый рабочий backend ещё не обновлён. UI не изображает успешную отправку, если API недоступен.
- Телефон/SMS/восстановление по коду не подключены. Вход по телефону обозначен недоступным; фальшивую отправку кода не добавляли.
- RNNoise, глобальный PTT поверх игры, администрирование/исключения, лимиты канала и сроков/числа применений приглашения из Design Lab требуют отдельных backend/native изменений.
- Не все 118 макетных состояний стали рабочими сценариями. Этот перенос покрывает авторизацию, основное голосовое представление, его ошибки, приглашение и настройки; полная функциональная паритетность не заявляется.
- Браузерный preview хранит сессию только в памяти. Обновление вкладки требует повторного входа.

## Следующий инфраструктурный шаг

Рекомендуемый путь: отдельный LiveKit на VM в РФ и TURN/TLS, затем проверка двумя участниками из целевых сетей. Это изменение инфраструктуры, а не ещё один переключатель клиента; гарантий до теста нет.

Официальная VM-схема LiveKit использует Docker Compose и Caddy, отдельные DNS-имена для сигналинга и TURN и порты 443/TCP, 7881/TCP, 3478/UDP, диапазон RTC UDP. Нельзя просто направить TURN через обычный HTTP reverse_proxy: нужен L4/TLS-маршрут официального генератора ([LiveKit VM deployment](https://docs.livekit.io/transport/self-hosting/vm/)). TURN/TLS без балансировщика должен быть доступен на 443 ([LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/)).

Порядок: отдельный staging → доступность DNS/TLS/портов → независимые токены двух участников → подтверждённое двустороннее аудио из реальных сетей → backup базы/постоянный JWT_SECRET → переключение LIVEKIT_URL и соответствующей пары ключей только вместе → возможность отката. Пользовательские аккаунты и членство в каналах сохраняются; менять токен-ключи без синхронного переключения сервера нельзя.

Существующие docker-compose.yml/livekit.yaml в репозитории являются старым черновиком (v1.7, без TURN/TLS). Они не описывают текущий LiveKit Cloud и не должны использоваться для production как есть. Покупка VM, настройка DNS и переключение работающего backend в этом обновлении не выполнялись.
